# 70. この先へ — 自分の課題に転移する

> ここまでで、エージェント = データツール + ループ + コンテキスト + 検証 + スキル + eval を、
> 引き算のはしごで 1 段ずつ観察しました。最後は、それを **自分のデータと業務課題** に
> 適用します。難易度順のメニューから、興味のあるものを選んでください。全部やる必要は
> ありません。**1 つを最後までやり切る** 方が学びが深いです。

ワークショップの場では **(選ぶ → 最初の一歩 → クロージングの一文)** まで。本体は
各自のペースで。実装は手打ちせず、**③開発プロンプト** で Claude Code などに書かせます
（テンプレートは [appendix-prompts.md](./appendix-prompts.md)）。詰まったら
[appendix-troubleshooting.md](./appendix-troubleshooting.md) と各スキル md 本文を頼ってください。

> **どのブランチで作業する？** 拡張は **`main`** で行います（全層がそろっているので、
> 検証もスキルも eval も使えます）。`git switch main` してから始めてください。

## (1) 組み込みデータセットを 1 つ増やす ★

**ゴール**: よく使うデータを `src/lib/ai/builtinDatasets.ts` に 1 行足し、以後はチャットで
名前を言うだけでエージェントが自分で読み込むようにする。

**ヒント**:

- `BUILTIN_DATASETS` 配列に `{ table, url, description }` を 1 つ追加するだけ。コード変更は
  この 1 か所（20 章で見たとおり、system prompt がこの配列を読んでモデルに教える②の層）。
- `url` は同一オリジンが安全。ファイルを `public/data/` に置き `${BASE_URL}data/<file>` に。
  外部 URL は CORS が要る（[appendix-troubleshooting.md](./appendix-troubleshooting.md)）。
- `description` に **列名と型・座標系** を書くと、モデルが探索を減らして正確に使える。

**学べること**: 「②の層に知識を持たせる」最短の形。system prompt 経由でモデルにデータを
教える発想（スキルと同じ原理）。

---

## (2) 自分の CSV を都道府県にコロプレス表示 ★

**ゴール**: 手元の CSV（都道府県別の何かの指標）を読み込み、`japan_prefectures` に結合して、
指標でコロプレス地図を作る。

**ヒント**:

- SQL タブか、チャットで「この URL の CSV を読み込んで」。CSV は `read_csv_auto`。
- 結合キーは都道府県名かコード。両テーブルを `DESCRIBE` して名前と型を合わせる
  （全角/半角・NFC の揺れに注意。`duckdb.basics` スキル参照）。
- `japan_prefectures` は GeoParquet なので `geom` は読込時点で `GEOMETRY`。自分で用意した
  空間データは `DESCRIBE` で型を確認し、`BLOB`(WKB)/WKT なら `ST_GeomFromWKB`/`ST_GeomFromText`。
- 結合結果を `CREATE TABLE` し、`SUMMARIZE` で指標のレンジを見てから `interpolate` の区切りに使う。

**学べること**: 属性テーブルとジオメトリの結合、`SUMMARIZE` 起点の色設計、自分のデータを
最短でエージェントに載せる流れ。

## (3) 業務で繰り返す作業をスキル化する ★★

**ゴール**: あなたが仕事で毎回やる分析・前処理・可視化の手順を、スキル md 1 枚にする。

**ヒント**:

- 50 章の形式で、`<domain>/<name>.md` として `src/lib/ai/skills/` に置く。
- frontmatter は `description`（「いつ必要か」を書く）/ `tasks`（英語＋日本語キーワード）/
  必要なら `deps`。本文は「いつ使うか」「具体的な SQL / spec の型」「よくある間違いと直し方」。
  既存の `duckdb/spatial.md` や `map/geospatial.md` の粒度が良いお手本。
- 追加後は **開発サーバを再起動**（スキルはビルド時 glob）し、`get_skill` のカタログに
  出るか確認。前後で挙動が変わることを確かめる。

**学べること**: 暗黙知を「エージェントが読める作法」に言語化する力。翌週から自分の業務に
効く、いちばん実用的な転移。

---

## (4) `buffer_analysis` ツールを「検証つき」で追加する ★★

**ゴール**: 指定テーブルのジオメトリに `ST_Buffer` を掛けた新テーブルを作る `buffer_analysis`
ツールを、**入力検証つきで** 実装し、さらに **eval を 1 つ** 添える。

**ヒント**:

- お手本は `duckdbQuery.ts`（4 部品の形）と `updateMapStyle.ts`（検証の入れ方・40 章）。
  `tool({ description, inputSchema(zod), execute })` を返す `createXxxTool(ctx)` 関数。
- 入力: `table` / `distanceMeters` / `outputTable`。**投影して（EPSG:4326 →
  例 EPSG:6677, `always_xy := true`）メートルでバッファ → 4326 に戻す**（30 章の軸順の罠）。
- **検証を入れる**（この課題の肝）: 対象テーブルにジオメトリ列があるか、距離が正か、
  出力テーブル名が有効かを execute の冒頭でチェックし、駄目なら `{ error }` を返す。
  「素朴ツールが沈黙して壊れる」（30 章）を、自分の手で防ぐ設計にする。
- `src/lib/ai/tools/index.ts` の `createTools` に **登録**（しないとモデルから見えない）。
- **eval を 1 つ**（60 章）: `src/evals/` に「バッファ依頼 → 出力テーブルが存在し行数 > 0」を
  検証するケースを足し、`npm run test:evals` で成功率を見る。

**学べること**: ツール設計（4 部品・単一責務）、検証の入れどころ、そして **自作ツールを
eval で守る** という成果物化まで一気通貫。

## (5) 自分のデータで end-to-end を通す ★★★

**ゴール**: あなたの業務データを 1 つ選び、**読み込み → 分析 → 可視化** をエージェント経由で
最後まで通す。必要なら **ツール 1 個 + スキル 1 枚** を設計して足す。

**ヒント**:

- ツール =「アプリが実際に実行する処理」、スキル =「その処理を正しく使う作法」。この役割分担
  （20/50 章）を意識して切り分ける。
- 「1 ツール = 1 責務」「description に使いどころを書く」「index.ts に登録」「必要なら検証」
  「回帰は eval で」——ここまでの全層を、自分の課題に当てる。
- 開発プロンプトのテンプレートは [appendix-prompts.md](./appendix-prompts.md)。

**学べること**: 転移ゴールそのもの——自分の課題に対してツールとスキルを設計し、その挙動を
API レベルで説明・デバッグできる状態。

## 発展データソース（各自のペースで）

- **PLATEAU（国交省の 3D 都市モデル）** — 配信サービス（`api.plateauview.mlit.go.jp`）の
  REST / GraphQL API でデータカタログ・配信 URL・属性を取得。JSON を `read_json_auto` で、
  GeoJSON/MVT を `ST_Read` で読み込み、建物属性（用途・階数・高さ）を `match`/`step` で
  塗り分ける。属性が多いので `DESCRIBE` で構造把握を丁寧に。
- **Overture Maps の巨大 GeoParquet** — DuckDB の `spatial` / `httpfs` で、ダウンロードせず
  `read_parquet('https://…')` から直接クエリ。`WHERE bbox…` と `LIMIT` で必要範囲だけ絞る
  （ブラウザ内 DuckDB-WASM はメモリ上限 4GB）。`geom` が `BLOB`(WKB) のままなら `ST_GeomFromWKB`。

## クロージング — 自分の言葉にする

最後は解説ではなく、**問い** で終えます。手を止めて、次の一文を書いてください。

> **あなたの仕事のデータで、エージェントに最初に持たせるツールは何ですか？
> その `description` を 1 文で書いてください。**

書けたら、隣の参加者と **交換** してみてください。相手の 1 文を読んで、
「そのツールはいつ呼ばれるべきか」「引数は何か」「何を返すべきか」が想像できるか話します。

`description` が書ければ、ツールが設計できます。ツールが設計できれば、エージェントが作れます。
その挙動を——10 章の「口だけ」から 60 章の「evals で守る」まで見てきた層の言葉で——
説明できるなら、あなたはこのワークショップの持ち帰りゴールに到達しています。

お疲れさまでした。越えられない壁は、もうありません。
