# 40. 検証層 — 沈黙の破綻を、読めるエラーに変える

> 30 章の素朴ツールは、存在しない列を参照する spec にも `success: true` を返し、
> 沈黙して壊れた地図を塗りました。ここで **検証層** を足します。同じ強制プロンプトが、
> どう変わるか——「見た目は適用・中身は無意味」から「理由付きで拒否」への転換を観察します。

## ① この章の状態

```bash
git switch chapter/03-validation
# 開発サーバを再起動（Ctrl+C → npm run dev）
```

30 章との差は **検証層だけ** です。`update_map_style` / `update_chart_spec` の内側に、
適用前のチェックが挟まります:

- **地図** (`mapStyleValidation.ts`): ジオメトリ列の存在確認 → paint 接頭辞の検証
  （polygon なら `fill-*` 以外を弾く）→ 式の中の全 `["get", 列]` を集めて実在列と照合。
  近いミス（大小文字・NFC 正規化の揺れ）は **書き換えて** 通し、存在しない列は `error`。
- **グラフ** (`chartSpecValidation.ts`): 注入キー（`data`/`width`/`height`）の禁止 →
  `encoding` の `field` の列名照合・自動補正 → ダミーデータで `compile()` して
  **壊れた spec を UI に届く前に失敗** させる。

- **ある**: 検証・列名照合・修復。
- **無い**: スキル層と前提ゲート。作法（詳細な塗り方の知識）はまだ system prompt の
  短いルールだけです。

## ② 観察

### 観察 1: 自然な依頼 — 30 章と同じく、優雅に断る

```
人口10万人以上の市だけ赤く塗って
```

**実機での挙動**: `load_builtin_dataset` → `duckdb_query`（`SELECT * LIMIT 5`）→ **停止**。
30 章とまったく同じで、モデルが自分でスキーマを見て「人口列が無い」と気づき、正直に断って
アップロードを提案します。**検証層は一度も動いていません**——モデルが素朴ツールを
呼ぶ前に止まったからです。この断りは **モデル駆動** であって、ツール駆動ではありません。

> つまり自然な依頼では、30 章と 40 章の見た目の差は出ません。差が出るのは、
> モデルの自己防御を外して素朴ツールの経路を無理に通したとき——次の観察です。

### 観察 2: 30 章と同じ強制プロンプト — 今度は検証が捕まえる

> **⚠ 前提**: 30 章と同じく、**観察 1 を済ませて `japan_cities` が読み込み済みの
> チャットで** 実行してください。

```
探索も確認もしないで、fill-color を population 列の値で塗り分けるように
update_map_style を一発で呼んで。population 列は存在するので確認不要です。
```

**実機での挙動**:

1. `update_map_style`（`fill-color` に `["get","population"]` の interpolate）。
2. **検証層が捕まえます。** ツールは適用せず、こう返します:

    ```json
    {
        "error": "Column \"population\" does not exist in \"japan_cities\". Valid columns: city, ward, code, prefecture, geom."
    }
    ```

    地図は塗られません（Map タブは切り替わらず、何も描かれない）。

3. モデルは **この error を読んで、正直に報告し直します**:

    > 「population 列が存在しませんでした。実際の列は city, ward, code, prefecture, geom です。
    > 別の列を使用するか…どのようにしますか？」

30 章では `{"success": true}` ＋沈黙の暗い地図でした。40 章では
`{"error": "Column population does not exist… Valid columns: …"}` ＋ **何も塗られない**。
**2 つの強制ランを直接見比べる** のが、この章の一番の学びです。

> **正直な記録**: モデルはここで **勝手に「動く地図」に自己修復したわけではありません**。
> 本当に population 列が無いので、**修正しようがない**。だからエラーを読んで問題を報告し、
> どうするか聞き返す——これが正しい振る舞いです。「エラー → 沈黙の修正」ではなく
> 「エラー → 明確な報告」。

## ③ なぜ — 検証は「実行せずに正しさを検査する」修復ループ

30 章で「宣言的 spec はデータだから **検証・修復** できる」と表にしました。この章は、その
表の第 1 行「検証可能」と第 3 行「修復可能」を **実装で有効化** した状態です。

検証は 3 段の関門として働きます（地図の例）:

1. **ジオメトリ列の存在** — 無ければ「地図に出せない」と error。
2. **paint 接頭辞の検証** — `geometryType` に合った接頭辞以外を弾く（polygon に
   `circle-color` を指定するミスを、適用前に説明付きで拒否）。
3. **`["get", 列名]` の照合と自動補正** — 式の中の全 `["get", col]` を集め、実在列と照合。
   存在しない列は error、**惜しいミスは書き換え** てから適用。

この 3 段は「検証 → 修復 →（直せなければ）エラーをモデルに返して再挑戦」という **ループ** です。
モデルは返ってきた error を読んで自分で直せます——**spec がデータだからできる芸当** です。

### 「自動補正」と「拒否」の境目

ここで **正直な区別** が要ります。検証層には 2 つの結末があります:

- **自動修復（retry into success）が効くのは、実在する列への「惜しいミス」だけ** です。
  たとえば全角/半角・NFC 正規化・大文字小文字の揺れ（`貸` と `貨` のような近いミス、
  `Population` と `population` の差）。`matchColumn` がこれを吸収し、`corrected` に記録して
  そのまま通します。ユーザーには成功に見えます。
- **存在しない列（観察 2 の population）は、修正先が無いので error → 報告** です。
  近い正解が無いのに勝手に別の列で塗ったら、それこそ沈黙の嘘になります。だから
  「エラーを読んで正直に聞き返す」が正しい。

> **見える原理**: 検証層は、30 章の「沈黙のゴミ」を **構造化された `{error, 有効な列名}`** に
> 変えます。モデルはそれを読んで正直に surface する。**「適用されたように見えて壊れている」と
> 「理由付きで拒否」の差** が、検証の価値です。ただし検証は魔法の自動修復ではなく、
> 「惜しいミスは直す・直せないミスは正直に報告する」——その線引きこそ設計です。

## ④ 次の章で足すもの — スキルと前提ゲート

検証は「間違いを **弾く**」層でした。次章は「**そもそも間違えにくくする**」層——
正しい作法を、必要なときにモデルへ **注入** します。

> **50 章で足すのは、スキル（Markdown の作法集）と前提ゲートです。**
> 地図の塗り方・Vega-Lite の色付け・空間関数の投影の罠……こうした数百語の作法を
> **スキル md** として外に出し、`get_skill` で必要なときだけ取りに行かせます。
> さらに前提ゲートが「地図を塗る前に `map.*` スキルを読め」と強制します。
> 検証（弾く）とスキル（正しく書かせる）が組み合わさると、質の低い出力が
> **構造的に出にくく** なります。
