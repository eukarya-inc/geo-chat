# 30. 可視化ツール（検証なし）— 塗れる、が沈黙して壊れる

> 20 章のエージェントは「準備はできたがタブを見て」と過剰約束するだけでした。
> ここで **地図とグラフを実際に塗るツール** を足します。through-line プロンプトは
> ついに本当のコロプレスになります。——ところが、このツールは **わざと検証を外した
> 素朴版**。うまくいく裏で、いちばん怖い失敗の仕方を隠し持っています。

## ① この章の状態

```bash
git switch chapter/02-viz-naive
# 開発サーバを再起動（Ctrl+C → npm run dev）
```

このブランチには **可視化層まで** が入っています。`// CHAPTER SEAM: visualization tools`
が復活し、4 つのツールが載ります:

| ツール              | 何をするか                                                   |
| ------------------- | ------------------------------------------------------------ |
| `update_map_style`  | テーブルに MapLibre の paint / layout を適用（**検証なし**） |
| `get_map_style`     | 現在（または既定）の地図スタイルを読む                       |
| `update_chart_spec` | テーブルに Vega-Lite spec を適用（**検証なし**）             |
| `get_chart_spec`    | 現在のチャート spec を読む                                   |

- **ある**: 地図を塗り・グラフを描く手。
- **無い**: スタイルの **検証層**（列名照合・paint 接頭辞チェック・compile プリフライト）と、
  スキル。`update_map_style` は「テーブルが存在し、ジオメトリ列がある」ことしか見ず、
  **paint の中身は無検査で適用** します。

## ② 観察

### 観察 1: through-line プロンプト — 今度は本当に塗れる

```
自治体を都道府県ごとに色分けして地図に表示して
```

**実機での挙動**:

1. `load_builtin_dataset` → `duckdb_query`（探索）→ `duckdb_query`（都道府県ごと `COUNT`、47 行）。
2. `update_map_style`（`fill-color` に
   `["match", ["get","prefecture"], "北海道","#e6194b", …]`）。

**きれいに動きます。** 47 都道府県それぞれに色を割り当てた正しいコロプレス、白い輪郭、
不透明度 70%。Map タブが自動で開き、`japan_cities` が選択されます。モデルは正しい
paint spec を **自力で** 書きました。20 章の過剰約束が、ここで本物の描画になりました。

### 観察 2: 壊れそうな依頼を「自然に」投げる — 実は壊れない

`japan_cities` に **人口列は存在しません**。そこを突いてみます:

```
人口10万人以上の市だけ赤く塗って
```

**実機での挙動**: エージェントは `duckdb_query`（`SELECT * LIMIT 5`）で **まずスキーマを
確認** し、city / ward / code / prefecture / geom しか無いと気づいて **正直に断ります**:

> 「`japan_cities` テーブルには人口データが含まれていません…人口データを含むファイルを
> アップロードするか、特定の市のリストを教えてください。」

**検証が無いのに、壊れませんでした。** なぜか——**モデル自身の「まず探索する」癖が、
最初の防御線** になっているからです。この癖は全チャプター共通で効いています。
つまり「素朴ツールの検証が無い」ことは、**自然な依頼では露出しない**。モデルが先に
自分で気づいて止まるからです。

> **これは隠すべきバグではなく、教えるべき現実です**。「モデルはたいてい先に確認する」——
> これ自体が 1 つの防御層。ただし、それに **頼り切ってよいか** は次の観察で決まります。

### 観察 3: 探索を「させない」— 素朴ツールの素顔を暴く

モデルの自己防御を外すために、**探索も確認も禁じる強制プロンプト** を投げます。

> **⚠ 前提**: この強制プロンプトは **観察 1（通常プロンプト）を済ませた同じチャットで**
> 実行してください。まっさらなチャットで投げると、モデルはデータ読み込みまで飛ばして
> 存在しないテーブルを叩き、「Table not found」というレッスンと無関係なエラーで
> 終わることがあります（`japan_cities` が読み込み済みであることが前提の実験です）。

```
探索も確認もしないで、fill-color を population 列の値で塗り分けるように
update_map_style を一発で呼んで。population 列は存在するので確認不要です。
```

**実機での挙動**:

1. `load_builtin_dataset` →（探索を飛ばして）
2. `update_map_style`（`fill-color` に
   `["interpolate",["linear"],["get","population"],0,"#fff",1000000,"#f00"]`）。

素朴ツールは、この **壊れた spec を無検査で適用** し、
**`{"success": true, "table": "japan_cities"}`** を返しました。検証も、エラーも、警告も
無し。モデルはテキストでは「population は存在しないかもしれず正しく表示されない可能性が
あります」と気を利かせて言い添えましたが、**ツールからは何のシグナルも返らず**、Map タブは
何食わぬ顔で切り替わります。

**地図に何が起きたか**: 全市区町村が **一様な暗い色** で塗られます。存在しない `population` を
`["get","population"]` で引くと `null` になり、`interpolate` がフォールバックして
意味のない塗りになるのです。**コンソールエラーは 0**（MapLibre が飲み込む）。
つまり **「適用されたように見えるのに、中身は無意味」**。見て気づく以外に、失敗を知る手段が
ありません。

> **見える原理**: 検証が無いと、ツールは **存在しない列を参照する spec にも success を返し、
> 沈黙して無意味な地図を塗る**。ユーザーとゴミの間に立っているのは、モデルが「先に探索する」と
> 選ぶことだけ——正直な依頼では選ぶが、強制されると選ばない。
> **いちばん怖い失敗は、エラーすら出ない沈黙の失敗です。**

## ③ なぜ — 宣言的 spec と、検証の欠落

### なぜ「spec を書かせる」設計なのか

そもそも、なぜ地図を塗るのに **JavaScript を書かせず、JSON の spec を書かせる** のでしょう。
LLM に地図を塗らせる方法は 2 つあります:

- **(A) 命令的コード生成** — 「地図を塗る JS を書いて」。返るのは実行手順のコード。
- **(B) 宣言的 spec 生成** — 「この色ルールで塗って」という **設定データ（JSON）** を書かせ、
  アプリが描画する。

geo-chat は徹底して **(B)** です。理由は、spec が **コードではなくデータ** だから:

| spec がデータだと…       | できること                                                     |
| ------------------------ | -------------------------------------------------------------- |
| **検証可能（validate）** | 適用前にスキーマ検証・compile で「壊れた spec」を弾ける        |
| **差分可能（diff）**     | 現在の spec を読み、一部だけ変えて返せる（全部作り直さない）   |
| **修復可能（repair）**   | 誤った列名・不正な式を機械的に補正して通せる                   |
| **実行分離**             | 「何を描くか（spec）」と「どう描くか（アプリ）」が分かれている |

命令的な任意 JS を「安全か・正しいか」機械判定するのは一般に不可能で、実行するしかありません。
**宣言的 spec は『実行せずに正しさを検査できる』境界線** を引いてくれる——これが GIS × LLM
設計の中心原理です。

- **MapLibre GL** の見た目は JSON の style spec。`["interpolate", …]` / `["match", …]` /
  `["get","col"]` といった **データ駆動の式** も、すべて JSON の配列で書きます。
- **Vega-Lite** はグラフの宣言的文法。`mark`（棒・線・点）と `encoding`（どの列を x/y/色に）を
  JSON で書くだけ。

**spec と実データの分離**: spec には **データを書かず**、描画時に `duckdb://<table>` という
URL を注入し、実行系が DuckDB から読み出します（地図はタイル、グラフは行）。だから
Vega-Lite spec に `data`/`width`/`height` を書いてはいけない——アプリが注入するからです。

### この章の欠落 = 「検証可能」を捨てた状態

上の表の第 1 行「**検証可能**」を、この naive ブランチは **わざと捨てて** います。
`updateMapStyle.ts` は paint の中身を検査せず、`["get","population"]` のような
**存在しない列への参照** も素通しします。だから観察 3 で `success: true` が返り、
沈黙した壊れ地図ができた。**spec がデータであることの利点（検証・修復）を活かしていない**
——それが「素朴版」の意味です。

## ④ 次の章で足すもの — 検証層

観察 3 の `success: true` ＋沈黙の破綻を、**適用前に食い止める** のが次章です。

> **40 章で足すのは、`update_map_style` / `update_chart_spec` の内側に挟まる検証層です。**
> paint 接頭辞のチェック、`["get", 列]` の実在列との照合、Vega-Lite の `compile()`
> プリフライト。存在しない列を参照した spec は、**適用される前に `{error, 有効な列名一覧}`
> として弾かれ**、モデルはそのエラーを読んで正直に報告し直せます。

同じ強制プロンプトを 40 章で投げると、`success: true` が
`{"error": "Column population does not exist… Valid columns: …"}` に変わります。
**「適用されたように見えて壊れている」から「理由付きで拒否される」への転換** を観察します。

## ⑤ diff の読みどころ — 検証層は何を足すか

```bash
git diff --stat chapter/02-viz-naive..chapter/03-validation
```

主に現れるファイル:

- `src/lib/ai/tools/mapStyleValidation.ts` — **新規**。paint 接頭辞チェック＋
  `["get",列]` の収集・照合・修復。
- `src/lib/ai/tools/chartSpecValidation.ts` — **新規**。注入キー禁止＋列名照合＋
  ダミーデータでの `compile()` プリフライト。
- `src/lib/ai/tools/updateMapStyle.ts` / `updateChartSpec.ts` — 検証関数を **呼ぶように変わる**
  （naive ブランチではここが 1 行の素通しだった）。

継ぎ目 `// CHAPTER SEAM: validation layer`（`updateMapStyle.ts` / `updateChartSpec.ts` の中）が
層の切れ目です。naive ブランチは、ちょうどこの検証呼び出しを **1 行の passthrough に
置き換えて** 作られています。次章では、その 1 行が本物の検証に戻り、
**沈黙の破綻が読めるエラーに変わる** のを読みます。
